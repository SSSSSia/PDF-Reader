# 阶段11：性能与并发体验（v0.13.0）

> 立项：2026-09-10，用户验收反馈原话——"整个软件总感觉用起来不顺手，有点卡顿，
> 以及不能同时进行多个操作，后端很容易卡住"。本阶段为**体验专项**：先量化、
> 后动手（T0 决策门），所有优化以实测数据为准，不拍脑袋。

## 1. 问题清单（用户体感 → 初步根因）

| # | 用户体感 | 初步根因分析 | 置信度 |
|---|----------|--------------|--------|
| P1 | 翻译/操作时界面卡顿 | **前端流式全量重渲染**（已证实）：translationManager 每个流式批次调 `pdfStore.setPages(pages)` 整表替换数组 → BilingualPage/InlinePage 整列表（数百卡片 × MarkdownText+KaTeX）全量重渲；`MarkdownText` 无 React.memo；块级操作（单块重翻/公式）也走同一 setPages 全量路径 | 高（代码实证） |
| P2 | 不能同时进行多个操作 | ① P1 的连带（流式更新期间 UI 主线程被重渲染占满，点击响应慢）；② 多会话+后台翻译+BabelDOC 导出叠加时，前端轮询定时器成倍增加（每个任务独立 setInterval）；③ 后端单 uvicorn 进程，翻译/BabelDOC 并发时 GIL 争用 | 中 |
| P3 | 后端很容易卡住 | ① pymupdf/OCR 提取已走 `asyncio.to_thread`（排除事件循环直堵）；② 但 to_thread 默认线程池上限 40+ 有限、CPU 密集任务仍占 GIL，重载时健康检查/配置接口延迟上升；③ babeldoc worker 子进程与后端无资源隔离约定（多 worker 并发时内存 1.3G+/个，2026-09-10 实测） | 中（需量化） |

## 2. 决策门：T0 性能基线（先量化再优化）

- [x] **T0 性能基线测量（✅ 2026-09-11 完成，判定：通过）**：工具
  `backend/tools/perf_baseline.py` 已沉淀（四场景 + RSS 采样，报告落
  `logs/perf-baseline-*.json`）。实测（DALK.pdf 19 页，翻译缓存命中，窗口 45s）：

  | 场景 | /api/health P50 | P95 | max | 备注 |
  |------|-----|-----|-----|------|
  | S1 无负载 | 3.2ms | 7.3ms | 42ms | backend RSS 139MB |
  | S2 翻译流水线 | 3.4ms | 8.1ms | 130ms | status P95 13.1ms |
  | S3 BabelDOC worker | 4.6ms | 8.8ms | 268ms | worker RSS 峰值 1299MB |
  | S4 翻译+BabelDOC 双负载 | 4.5ms | **8.2ms** | 547ms | worker 1530MB；status P95 26.5ms |

  - 后端：流式翻译 + BabelDOC 并发下 health P95 ≈ 8ms，**远低于 200ms 验收线**
  - 内存：backend 151MB 平稳；单 worker RSS 峰值 1.5GB（与 09-10 实测一致）
  - 前端 Profiler 记录方法（人工，量化可选）：React DevTools → Profiler → 录制
    流式翻译 30s → 看 commit 时长分布（火焰图按耗时排序）；DOM 节点数在控制台
    执行 `document.getElementsByTagName('*').length`。T1 memo 化后未变更块应
    出现在"did not render"列表
  - **判定**：后端请求响应性全面达标 → 按"达标项不动"裁剪 T2/T3（见下）

## 3. 任务分解

- [x] **T1 前端渲染优化（✅ 2026-09-11 完成）**
  - `MarkdownText` 包 `React.memo`（props：原文/译文/缩放/样式，均为值类型，易做浅比较）
  - 流式更新细粒度化：pdfStore 增加 `updateBlock(page, blockId, patch)` 局部更新路径，
    translationManager 批次只替换变化的块；页列表组件按页拆分 + memo，未变更页不重渲
  - 块级操作（重翻/公式回填）同走局部更新，不再整表 setPages
  - 会话切换（activate 快照交换）天然整表替换，保留
  - 实施记录：`applyBlockPatches(patches)` 单次 set 批量不可变补丁（未触及页/块
    引用不变，与阶段8 captureActive/activate 快照语义兼容）；translationManager
    轮询改「diff → 补丁」，结构变化（提取期新页/新块）兜底整表 setPages；
    BilingualPage/InlinePage 抽 memo 行组件（BilingualBlockRow/InlineBlock）+
    isPureImage 提模块级 + flatMap useMemo。块级操作（重翻/公式回填）探索确认
    早已走 updateBlockTranslated/Original 局部路径，无需改动。量化收益待 T0

- [ ] **T5 翻译任务自动重接管（2026-09-11 用户确认立项；F5/刷新后一键恢复）**
  - 背景：翻译进行中 F5 整页重载，前端丢失 job_id 无法续跟，任务在后端孤儿化
    继续跑（跑完正常落缓存/索引，不丢数据）；用户需手动重开文档再点一次翻译
    才能接管。job_id 具备确定性（内容哈希前16位_mtime），具备自动重接管条件
  - 后端：processor 的 job dict 目前未存 file_path——先补存；新增「列出运行中
    任务」端点（`GET /api/pipeline/running`，返回 `[{job_id, file_path, progress}]`，
    数据源与 `running_job_count()` 同源）。接口同步总纲 §4.4 与 README API 表
  - 前端：translationManager 增加 `attach(jobId, filePath)`（复用现有 poll 循环）；
    应用启动/进入文献库时查询一次 running 列表，发现本地存在对应文件的未完成
    任务 → 自绘提示「检测到未完成翻译：xxx，是否继续？」→ 确认后 attach 恢复
    进度与流式渲染
  - 验收点：翻译中 F5 → 提示出现 → 确认后进度/译文无缝恢复；全程无重复计费；
    无翻译任务时查询不产生任何打扰
  - 约束：同文件重复提交后端本就幂等复用（hash+mtime），本任务只解决「前端
    自动发现并接管」，不改 run_pipeline 幂等逻辑

## 4. 风险与缓解

| 风险 | 缓解 |
|------|------|
| 局部更新改坏阶段8 会话快照语义 | captureActive/activate 保持整表快照不动，只优化流式路径；快照交换用例补回归 |
| 多进程 uviton 分裂内存任务表 | 默认维持单进程；多进程仅作评估项，不默认实施 |
| qps 提高后 SiliconFlow 429 波动 | BabelDOC 内置 tenacity 重试兜底；T2 队列上限防雪崩 |
| 优化过度设计 | T0 gatekeeper：基线不达标项才做，达标项不动 |
