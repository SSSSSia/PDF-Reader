# 阶段11：性能与并发体验（v0.13.0）

> 立项：2026-09-10，用户验收反馈原话——"整个软件总感觉用起来不顺手，有点卡顿，
> 以及不能同时进行多个操作，后端很容易卡住"。本阶段为**体验专项**：先量化、
> 后动手（T0 决策门），所有优化以实测数据为准，不拍脑袋。

## 1. 问题清单（用户体感 → 初步根因）

| # | 用户体感 | 初步根因分析 | 置信度 |
|---|----------|--------------|--------|
| P1 | 翻译/操作时界面卡顿 | **前端流式全量重渲染**（已证实）：translationManager 每个流式批次调 `pdfStore.setPages(pages)` 整表替换数组 → BilingualPage/InlinePage 整列表（数百卡片 × MarkdownText+KaTeX）全量重渲；`MarkdownText` 无 React.memo；块级操作（单块重翻/公式）也走同一 setPages 全量路径 | 高（代码实证） |
| P2 | 不能同时进行多个操作 | ① P1 的连带（流式更新期间 UI 主线程被重渲染占满，点击响应慢）；② 多会话+后台翻译+BabelDOC 导出叠加时，前端轮询定时器成倍增加（每个任务独立 setInterval）；③ 后端单 uvicorn 进程，翻译/BabelDOC 并发时 GIL 争用 | 中 |
| P3 | 后端很容易卡住 | ① pymupdf/OCR 提取已走 `asyncio.to_thread`（排除事件循环直堵）；② 但 to_thread 默认线程池上限 40+ 有限、CPU 密集任务仍占 GIL，重载时健康检查/配置接口延迟上升；③ babeldoc worker 子进程与后端无资源隔离约定（多 worker 并发时内存 1.3G+/个，2026-09-10 实测） | 中（需量化） |

## 2. 决策门：T0 性能基线（先量化再优化）

- [ ] **T0 性能基线测量（gatekeeper）**：产出一份可复现的量化报告，未通过则本阶段不实施：
  - 前端：React Profiler 测「30 页文档流式翻译中」的帧率/单次提交耗时、长任务列表 DOM 节点数
  - 后端：流式翻译 + BabelDOC 导出并发时，`/api/health` P95 延迟、`/api/pipeline/status` P95 延迟
  - 内存：双 worker 并发时后端进程 RSS 曲线
  - 工具沉淀：`backend/tools/perf_baseline.py`（后端压测）+ 前端 Profiler 记录方法说明

## 3. 任务分解

- [ ] **T1 前端渲染优化（P1 主攻，预期收益最大）**
  - `MarkdownText` 包 `React.memo`（props：原文/译文/缩放/样式，均为值类型，易做浅比较）
  - 流式更新细粒度化：pdfStore 增加 `updateBlock(page, blockId, patch)` 局部更新路径，
    translationManager 批次只替换变化的块；页列表组件按页拆分 + memo，未变更页不重渲
  - 块级操作（重翻/公式回填）同走局部更新，不再整表 setPages
  - 会话切换（activate 快照交换）天然整表替换，保留
- [ ] **T2 并发与队列（P2）**
  - 轮询合并：多任务共用一个 1s 心跳 tick（单 setInterval 分发），取代每任务独立定时器
  - 后端任务并发上限与排队：同时翻译任务 ≤2、babeldoc worker ≤2（超出排队，前端显示排队位次）
  - 前端「新翻译期间打开旧文档」路径复验（阶段8 语义在重负载下不回退）
- [ ] **T3 后端响应性（P3，以 T0 数据为准裁剪范围）**
  - 重 CPU 操作（attach_block_bboxes、file_hash、缩略图）统一走专用 `ProcessPoolExecutor`（绕 GIL），
    事件循环线程池只留 IO 型任务
  - uvicorn `--workers` 评估（注意：内存任务表 `_jobs` 会随多进程分裂——若引入须把任务表
    外置或保持单进程 + 线程池方案，**接口契约不变**）
  - babeldoc worker 内存上限告警（RSS 阈值落日志）
- [ ] **T4 回归与验收**
  - 既有功能全量回归（pytest + tsc + build + 人工跨模式）
  - 按 T0 同口径复测，帧率/P95 达标线：流式翻译中前端无可感知卡顿（≥50fps）、
    并发重负载下 `/api/health` P95 < 200ms

## 4. 风险与缓解

| 风险 | 缓解 |
|------|------|
| 局部更新改坏阶段8 会话快照语义 | captureActive/activate 保持整表快照不动，只优化流式路径；快照交换用例补回归 |
| 多进程 uviton 分裂内存任务表 | 默认维持单进程；多进程仅作评估项，不默认实施 |
| qps 提高后 SiliconFlow 429 波动 | BabelDOC 内置 tenacity 重试兜底；T2 队列上限防雪崩 |
| 优化过度设计 | T0 gatekeeper：基线不达标项才做，达标项不动 |
