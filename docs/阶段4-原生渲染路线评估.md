# 阶段 4：原生渲染路线评估（决策门 · D6）

> **状态**：⬜ 未开始 ｜ **前置**：阶段 1–3 全部完成且用户人工验收满意度的**天花板仍不满足**时才启动
> **性质**：**这是决策文档，不是开发任务**。产出是 D6 决策记录，不是代码。
> **硬约束**：总纲第 2 章锁定技术栈、第 7.1 条"不得替换已锁定技术栈"——本阶段任何结论需以**新决策 D6** 形式经用户确认后方可动工。

## 1. 背景与证据

- Markdown 重建路线（pymupdf4llm → 自排版）的天花板：`position` 丢坐标、多栏阅读顺序偶发串行、矢量图形无法提取、PDF 原生公式是 Unicode 碎字符。
- 知云/靠岸的 100% 保真来自：PDF 原生渲染 + 文本层坐标提取 + 译文按坐标对照。
- 阶段 1–3 完成后本路线预期可达 ~80 分（干净、灵活、成本可控）；是否冲最后 20 分，取决于本评估。

## 2. 候选方案

| 方案 | 描述 | 保真度 | 工程量 | 风险 |
|------|------|--------|--------|------|
| **A 维持现状** | 阶段 1–3 后的 Markdown 路线，持续小修 | ~80 分 | 0 | 无；接受天花板 |
| **B 混合坐标路线** | PyMuPDF `page.get_text("dict")` 提取 block bbox → 页面渲染为背景图 → 译文按 bbox 贴坐标 overlay（双栏模式用，紧跟模式保留 Markdown 流） | ~90 分 | 中（1–2 周） | bbox 合并策略复杂（一个视觉段落多个 bbox）；多栏顺序仍需推断 |
| **C PDF.js 原生渲染** | pdfjs-dist 渲染页面（已引入，现仅缩略图）+ 文本层 span 定位 + 译文行内替换/对照（知云模式） | ~100 分 | 高（2–4 周） | 文本选择/字体嵌入/双栏重排交互复杂；与 Tauri webview 兼容需验证 |

## 3. 评估维度（决策时逐项打分）

1. **保真度**：多栏、公式、矢量图、表格、页眉页脚的还原度（用 3 份典型论文实测）。
2. **工作量**：含学习曲线与调试的日历时间。
3. **风险**：与现有 Tauri/React 架构的兼容性、性能（大 PDF 渲染内存）。
4. **可回退性**：B/C 是否可以只作为"双栏模式"的渲染层、紧跟模式保留现有实现（建议：是，天然降级路径）。
5. **维护成本**：开源复刻者能否按文档复现。

## 4. 原型验证计划（Spike，1–2 天，决策前必做）

- [ ] S2：pdfjs-dist 全页渲染 + 文本层 span 定位 demo（单页即可），在 Tauri webview 里跑通（C 方案可行性核心）。

## 5. 决策规则（预注册，避免沉没成本绑架）

- Spike 中 **B 方案 bbox 对应率 ≥ 90%** 且用户认为 90 分够用 → 选 B。
- 用户明确要知云级体验（100 分）且接受 2–4 周 → 选 C。
- 两个 Spike 都不及预期 或 用户对阶段 1–3 的 80 分已满意 → 选 A（本阶段关闭，路线图终版）。
- **Kill criteria**：任何方案实施中途发现核心假设不成立（如 bbox 合并不可行 / webview 性能不可接受），立即停下回到 A，不追加沉没成本。
