# 阶段 8：多会话阅读与后台翻译（v0.10.0）

> **状态**：🔨 开发完成，待人工验收（2026-09-09；T1–T4 落地，T5 自动化回归通过） ｜ **前置**：阶段 6 开发完成（文档库/文件夹基建） ｜ **依据**：用户需求 2026-09-09（翻译途中无法打开其他文献；期望"打开文章 = 新开软件内页面，可继续打开其他文章，与翻译互不冲突"）
> **目标一句话**：阅读多篇文献互不干扰（每篇一个独立会话页签），翻译在后台进行，翻译中可随意打开/切换其他文献。

---

## 1. 背景与证据

- 用户反馈（2026-09-09 截图）：翻译进行中点击文献库后，①无法再进入翻译实时进度页（已用过渡方案修复：进度卡可点击）；②点击其他已翻译文献无反应——这是阶段 6 验收期加的互斥守卫（`MainPage.handleOpenDoc` 中 `isLoading` 直接 return）。
- **根因是前端单会话架构，不是后端并发能力**（用户问询"是否需要升级后端并发"）：`backend/pipeline/processor.py` 的 `run_pipeline` 本就每任务一个 `asyncio.create_task`，`_jobs` 字典支持多 job 并发（MAX_JOBS=50，完成即淘汰）；`POST /api/docs/open`（`open_cached_doc`）无状态、纯缓存读——后端天然支持"N 路阅读 + 翻译并行"，无需升级。
- 前端瓶颈：`src/stores/pdfStore.ts` 是全局单例（单份 `file/filePath/pages/currentPage/result`），翻译轮询（`useOcr.processFile`）与阅读会话共用同一份存储，并发访问会互相覆盖——互斥守卫是权宜之计。
- 关键耦合点已核实：`OriginalReader.tsx` 的 pdfjs 文档初始化依赖 `useEffect [filePath]`（换会话自动重建）；块级操作（式/单块重翻/译制图）都经 pdfStore 的 `updateBlock*` 作用于"当前活跃会话"，多会话下语义正确。

## 2. 范围

**做**：会话注册表（sessionsStore，快照交换式多开）、翻译管理器（轮询脱离阅读组件、后台进行）、阅读页顶部页签条（切换/关闭/翻译进度徽标）、文献库集成（解除打开互斥、翻译中卡片可进入）、会话内存上限（LRU 淘汰）。
**不做**：并行多翻译任务（首期保持同时 1 个翻译，第二次添加给予明确提示；架构预留扩展）；会话持久化到磁盘（重启即清空，文献库秒开兜底）；每会话独立阅读模式（readerMode 仍全局）；跨设备同步。

## 4. 验收标准（全部满足才算完成）

1. 翻译进行中：可打开任意已翻译文献阅读并来回切换，内容/滚动位置互不串扰；点击翻译中进度卡或页签可进入实时进度页（原文渐进渲染、译文逐段流入）。
2. 打开 ≥3 个文献形成 ≥3 个页签，页签条显示标题、当前页签高亮；关闭非活跃页签不影响其他会话；关闭全部回到文献库。
3. 翻译进行中再次添加文章：得到明确提示（不静默失败、不破坏进行中的任务）；翻译完成后文献库自动出现新卡片，页签进度徽标消失。
4. 会话超过 8 个时最久未访问的非翻译会话被自动淘汰，应用不崩溃、活跃会话不受影响。
5. 块级操作回归：式识别/单块重翻/译制图在切换会话后仍作用于当前阅读的那一篇。
6. `npx tsc --noEmit`、`npx vite build`、后端 pytest 全过。

## 5. 风险与缓解

| 风险 | 缓解 |
|------|------|
| 快照交换瞬间组件读到新旧混合状态 | 交换为单次同步 set（原子替换全部字段）；阅读组件均以 pdfStore 单一来源渲染 |
| 多会话 pages 常驻内存（长文档） | MAX_SESSIONS=8 + LRU 淘汰；pages 为纯文本+坐标（无位图），单篇数百 KB 量级 |
| 翻译中会话被误关闭/淘汰 | 翻译中页签不显示关闭按钮；LRU 跳过翻译中会话 |
| OriginalReader 对 filePath 变化的重建时序 | 依赖既有 `[filePath]` effect（阶段5 已验证模式）；切换会话时如处于原版模式，重建期间显示加载态 |
| 旧互斥逻辑残留（双路径入口） | T4 统一收敛到 sessionsStore/manager，删除守卫代码；grep 复查无 `isLoading` 打开拦截残留 |
